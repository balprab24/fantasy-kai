# League plan S1 — Sleeper import and My Teams, 2026-10-30

Branch `feat/leagues-s1` from `9797b2f` (PR #75 merged). Built and reviewed by Claude Code
against Part B S1 of `docs/research/2026-10-28-leagues-trades-plan.md`.

## What was built

**Schema (V11).**
- `league_connections`, `leagues`, `league_teams`, `league_rosters` and `league_matchups`.
- One copy per member. Every table carries `user_id`, and each child reaches its league through
  a composite `(league_id, user_id)` key, so a row cannot claim one member while pointing at
  another member's league.
- `ck_league_connections_sleeper_holds_nothing` makes it impossible to store a Sleeper credential.
- No points are stored.

**Backend, `com.fantasykai.leagues` (20 files):**
- the `LeagueProvider` seam and `SleeperLeagueProvider`;
- `SleeperScoringMapper` and `Unmodeled`;
- `RosterSlot`;
- `LeagueHttp`: four hosts on an allowlist in code, https only, redirects refused, a 2 MB cap and
  a 10 s timeout;
- `LeagueLimits`: Sleeper's budget shared across members at 600/min, a 5-minute cooldown per
  league, failing closed;
- `LeagueService`, `LeagueRepository`, and the controller with seven routes.

**Frontend.**
- `/teams`: the leagues list, and the Connect Sleeper flow (discover, then import).
- `/teams/[id]`: the roster by slot, scoring with unmodelled notices, standings, the remaining
  schedule, Sync now, choosing your team, and remove.
- My Teams moved from Coming into the primary nav; `/teams` added to `MEMBER_ROUTES`.

**Deliberate departures from the plan:**
- **"Which team is yours?" comes after import, not before.** The team is pre-selected where the
  Sleeper `owner_id` or a co-owner matches, and `PUT /leagues/{id}/my-team` changes it. Asking
  first would cost two calls per discovered league.
- **The import body carries the username.** The server then checks that the league is in that
  account's own list. Sleeper is public, so without that check any league id would import under
  any username.
- **Container width is 1440px, from DESIGN.md.** The plan said 1320px; DESIGN.md owns the fact.
- **Override-first resolution of roster ids, in SQL.** Rosters carry only Sleeper ids, so the
  full name matcher has nothing to work on. A stored id held by two players is refused.

## Invariants, against the diff

| Question | Answer |
|---|---|
| Is a computed point value persisted? | **No.** `fpts` is never read. A test asserts that neither "fpts" nor the fixture's points appear in a response, and `Team` has no points component. |
| Is an index added to `player_game_stats`? | No. The roster lookup uses V2's `idx_players_sleeper_id`, measured at 0.196 ms for 15 ids on the local database. |
| Is a stat named outside `StatKey`? | No. The mapper iterates `StatKey.values()` and matches on `json()`. Sleeper's own keys appear only as the platform's names. |
| Is anything rounded before the API boundary? | Only Sleeper's rates, to 4 dp to remove float32 noise. They are rates, not points; `ScoringEngine` is untouched. |
| Is SQL built by concatenation? | No user input reaches SQL text. `LEAGUE_COLUMNS` is a constant; injection through every new parameter is a test. |
| Did `ddl-auto` move, or an applied migration change? | No. V11 is new. |
| Is an external signal mandatory for a ranking? | No. League import is its own surface; every board works without it. |
| Is league data fetched as the user and never aggregated? | Yes. One copy per member, membership checked against the account's own leagues, nothing shared across members. |

## Browser QA

The servers ran from this worktree: the API with ingest and projection jobs disabled, and
`next dev` restarted with a clean `.next/dev`. A throwaway `@example.test` account was registered
through `/register` and deleted afterwards.

**Exercised live:**
- the nav;
- the `/teams` empty state;
- client-side username validation, which made no request;
- an unknown username: one live Sleeper call answered `200 null`, so the API returned 404 and
  the member read "No Sleeper user is named …" (confirms plan A1 against the real API);
- Sync on a league id Sleeper does not have: 404 with "No Sleeper NFL league has id …";
- a second sync: 429 with the cooldown sentence;
- **Not yours?**: PUT 200, the heading and roster changed;
- remove with the inline confirm: back to `/teams`, with the league, its connection and its
  ruleset gone and no orphan rows;
- a fresh load: no console errors, and no horizontal scroll at 1710px.

**Seeded, not imported.** The populated league page was rendered from a league inserted by SQL
for the QA account: real players by name, a D/ST, two unmatched spots, a DL slot and grouped
unmodelled scoring. It shows the page renders those states. It is **not** evidence that a real
Sleeper import produces them; `LeagueApiTests` covers that path against fixtures.

**A dev-only hydration mismatch.** After `nav.ts` changed under a running `next dev`, the server
rendered the old nav. Restarting with a clean `.next/dev` cleared it, and a fresh load showed no
errors.

## What I did not fix, and why

- **The real-league acceptance gate is open.** It needs the owner's Sleeper username or league
  id to capture a redacted fixture. Until then the fixtures are synthetic, shaped on a captured
  league.
- **Future-week pairings are unverified on a live 2026 league.** The code treats an unpaired
  week as absent and refetches it on a later sync, never as a bye. Whether Sleeper publishes
  future pairings is still open.
- **A failed sync still spends the 5-minute cooldown.** It protects the shared budget; the cost
  is a member waiting after a Sleeper outage. This is the owner's call.
- **Missing wins or losses read as 0** (`asInt(0)`). That is a default hiding an absence, but
  Sleeper always sends both in the captured shape.
- **Sleeper `settings.type` 1 and 2 (keeper and dynasty) are unverified.** They are imported and
  labelled, but plan scope is redraft.
- **The season-phase rules in `remainingWeeks`** for `pre` and `off` are a judgement, tested but
  not observed live outside the regular season.
- **Deploy order.** Vercel deploys `main` on merge; the API is deployed by hand. Merge this before
  the API is deployed and production `/teams` calls routes that 404. Deploy the API (V11) first,
  or together.
- **Phone width not checked.** The Chrome window would not resize. The layout uses the Scoring
  page's grid, which collapses to one column below lg.
- **`GET /leagues` makes one teams query per league** to name the member's team. That is fine at
  a handful of leagues per member.

## The argument against merging as written

My Teams goes into the primary nav before it can say anything a member can't already see on
Sleeper. There are no points, no projections and no trade values until S2 and S3. Putting it in
the nav now promises a product the page doesn't yet deliver; the case for holding it in "Coming"
until S2 is real.

The second argument: one copy per member multiplies storage and Sleeper calls by the number of
members in a league. That is the price of "never aggregated", and the plan accepted it.

What would show it wrong: members finding the page useless until S2, or a popular league's
members together spending the shared budget.
